# 2026-09-19 16:25 CDT - Node 22 base image, keep build toolchain as prebuild fallback
- **Change:** Dockerfile moved from node:20-bookworm-slim to node:22-bookworm-slim in all three stages (node 20 is EOL, team standard is node 22). The apt-get install of python3/make/g++ in the deps stage was first removed, then restored, in the same PR (#39).
- **Why:** better-sqlite3@12.10.0 ships a prebuilt binary for node 22 linux-x64 (ABI 127), proven by a clean docker build with the toolchain removed and a throwaway container serving 200 on /. But the first attempt of that same build hit a prebuild-install network timeout, with no compiler to fall back to, and failed outright; an unchanged retry then succeeded. A prebuild is an optimization, not a dependency, and a build that fails on a flaky network is worse than a slightly larger builder stage. The toolchain was restored and confirmed to live only in the deps/build stages, never copied into the runtime image (the run stage only takes .next/standalone, .next/static, and data from the build stage, no node_modules).
- **State after:** lumen-analytics's Dockerfile is on node:22-bookworm-slim with the apt toolchain kept as a fallback. docs/demos/lumen/decisions.md records the same reasoning. PR #39 open, not merged.
- **Refs:** PR #39 (Ginkobaloba/lumen-analytics), docs/demos/lumen/decisions.md (2026-09-19: Node 22 base image), demo-axlepoint PR #27 (same change, same reasoning)
- **Do not delete the toolchain later:** an independent deep verify (2026-09-19) proved the fallback is load-bearing. Pointing better-sqlite3's prebuild binary host at the discard port forced a real prebuild failure; with python3/make/g++ present, node-gyp compiled the module and the compiled module loaded and ran a query. Deleting the apt line reproduced a hard failure, "Could not find any Python installation to use", with a non-zero build exit. The toolchain looks redundant in a normal build precisely because the prebuild usually succeeds, so a future reader should not remove it on that basis.
